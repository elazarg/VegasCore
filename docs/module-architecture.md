# Module architecture

| Layer | Responsibility |
| --- | --- |
| GameTheory | Separately managed probability and game-theory foundation. |
| GameTheoryExtensions | Protocol limits, belief transport, enforcement and probability adapters. |
| Interaction | Signed message networks, partial observation, recall, execution and evidence. |
| Vegas.Foundation and Vegas.Expr | Typed contexts, values and expressions. |
| Vegas.Source | The source language, source information and evaluation. |
| Vegas.EventGraph | Typed dependencies, source-event execution and observations. |
| Vegas.Pending | Runtime packet submission, inclusion, deadlines and pending-message laws. |
| Vegas.Compile | Source-to-graph compiler and correspondence. |
| Vegas.Game | Strategic composition, source equilibrium extension, runtime preservation and obstruction proofs. |
| Test libraries and Paper | Regressions and axiom guards for results stated in the paper. |

[Paper](../Paper.lean) states the paper-facing theorems and pins their axioms.
Every mathematical result or invariant stated in the maintained manuscript is
pinned, including prose claims and examples, and nothing else is: the build
rejects `sorry` and the source policy rejects axiom declarations and trust
escape hatches throughout the tree. Dependency reachability does not
determine paper coverage. Technical import exceptions require an explicit
reason and a separately checked audit.
The [consolidation ledger](consolidation.md) records the target of the
development, its remaining steps, and the index of results retired to the
`research-tree` tag.

Search with rg and inspect signatures with lean-defs.py before adding machinery.

The admitted broadcast-existence draft in [Paper](../Paper.lean) is a
formalization target, not a checked manuscript result. Its
[implementation carrier](../Vegas/Game/BroadcastImplementation.lean) belongs to
the strategic composition layer. It contains no compiler constructor and does
not yet enforce the broadcast operational specification. The concrete compiler
and runtime definitions belong to their respective owning layers.
The [SE runtime design](se-runtime-design.md) specifies how to reuse those
layers across the existing sequential and proposed fixed-window concurrent
implementations, without making the latter's proof assumptions universal.

Model-specific namespaces may use the same mathematical theorem name. Cite the
qualified declaration to identify its contract. The documentation checker
rejects ambiguous short names; the reachability report follows actual constant
dependencies and accepts lexical references only when they identify one owner.

The lists below link the modules that have a description, by layer. Each
directory's aggregator imports every module in it.
